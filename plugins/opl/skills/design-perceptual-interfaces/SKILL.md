# Design perceptual interfaces

Make the intended relationship, action, and strength of evidence perceptible.
Give substantial design problems visual exploration and executable observation.
Keep the amount of work proportional to the uncertainty in the request.

## Choose the smallest useful route

| Request | Work |
| --- | --- |
| Change `bleep` to `bloop`; adjust a known spacing or color token without changing meaning | Make the edit and use the existing relevant check. Stop. Create no design packet, images, comparison, episode, or Projector record. |
| Repair a local hierarchy, legibility, affordance, or transition problem | Inspect the affected state, make one explicit hypothesis, change it, and inspect the result. Load only the relevant reference below. |
| Establish a visual direction or change consequential representation, relationships, uncertainty, or interaction | Use the evidence loop below. Expand only the parts that can change a design decision. |

A label that changes the action promised to the user belongs to the second route.
An explicit invocation does not make a tiny edit a redesign. Do not run this
procedure for every frontend change or create a task just to classify the request.

## Work inside the current workflow

The native root owns scope, planning, assignments, accepted meaning, and completion.
Read the existing design context and reuse its evidence. When Projector is active,
use [its existing contracts](references/projector.md). Return proposed meaning or
Lens changes to their owner. This skill creates design evidence, not another
scheduler, task registry, approval gate, or acceptance authority.

## Close the design loop

1. **Meaning.** Identify what changes, what stays true, intended interpretation,
   harmful misreading, and available action. Use a compact
   [perceptual contract](references/perceptual-contract.md) where meaning is at risk.
   Preserve observation, inference, intention, and advice as different things.
2. **Visual search.** For genuine direction work, explore structurally different
   representations with existing references, runnable specimens, or available
   image generation. [Extract a visual grammar](references/visual-search.md) from
   the selected hypothesis. Keep its useful decisions and reject semantic errors.
   A generated image is a hypothesis, not implementation evidence.
3. **Motion.** Specify the event, identity, source, reversibility, interruption,
   and expression. Use [semantic motion](references/motion.md) and relevant
   [runnable specimens](specimens/index.html). Preserve meaning without motion.
4. **Implement and observe.** Make the selected design real through the current
   product implementation. Use its native test/replay boundary or the optional
   [observation tools](references/workbench.md). Inspect real pixels and exercise
   real controls. Repair concrete deviations, then recheck affected evidence.
5. **Judge separately.** Record semantic correctness, comprehension/control, and
   aesthetic preference separately. [Compare and learn](references/evaluation.md)
   from observed choices and corrections. A model's selection is provisional;
   never attribute it to the user or convert it into proven comprehension.

Deliver the implemented result, its design rationale, inspected states and
interactions, evidence pointers, and remaining limits. Keep important corrections
with their context for future retrieval. Stop when the scoped obligation is met;
do not manufacture an episode or comparison after an ordinary successful edit.
