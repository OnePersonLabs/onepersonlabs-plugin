# Write and maintain useful documentation

Help the reader complete a real task and recognize its result. Documentation is
part of the product's usable interface. Preserve the project's voice, useful
structure, and accepted meaning; do not impose a standard page set.

## Establish the reader and task

Identify the audience, intended action, starting knowledge, and supported version
or environment. For a README, default to prospective users unless the project
specifies another audience. Read existing entry pages and their relevant links
before adding pages. Separate current capability, intended direction, experiments,
and dated evidence. Keep actionable status with its existing owner.

Choose a bounded reader journey: the starting state, action, observable result,
and consequential limitation or recovery. A concept page can explain a relationship
without invented steps. A troubleshooting page starts with a recognizable symptom
and leads through discriminating checks to recovery or an explicit unresolved state.

## Ground the instructions

Reuse the investigation and evidence already available in this task. Trace the
relevant public entrypoint through its actual consumer. Verify commands, flags,
UI labels, prerequisites, permissions, defaults, output locations, and outcomes
against current implementation or applicable observed behavior. Follow a handler,
translation, helper, or dependency when it can change what the reader must do.

Read only what can change the documented journey. A source index is navigation,
not proof of freshness. If a label or behavior remains unresolved, narrow or
qualify the claim and identify the gap; do not invent a plausible instruction.
Source inspection establishes implemented intent, not successful runtime operation.
Respect authorization before executing examples that modify state, publish, spend
money, or run experiments. Keep evidence anchors in existing project records when
they help maintain a consequential claim; do not require a new provenance schema.

## Write the shortest complete path

Give a README a clear purpose, suitable audience, first useful task, expected
result, material limitations, and routes to deeper information. Put internal
terminology and contributor mechanics where the reader needs them. Link to the
owning guide instead of duplicating a long procedure. Preserve historical receipts
as dated evidence, outside the main first-use path.

Write steps as actions in the order the reader performs them. State prerequisites
before they block progress. Use the actual control names and copyable command
blocks with the appropriate shell. Explain how to recognize completion and what
to do for a consequential failure. Keep qualifications close to the claims they
limit; do not bury them in a generic disclaimer.

Use images only when they resolve a specific recognition or spatial difficulty.
Prefer existing applicable captures; label mockups and reconstructions explicitly.
A rendered illustration does not prove runtime behavior. Commands remain text.
For substantial conceptual explanation or representation choices, use
$onepersonlabs:build-understanding; simple guides do not need another workflow.

## Maintain from the change outward

For an update, identify which reader actions, prerequisites, results, or limits
changed. Search affected entry pages, linked guides, and examples for those claims.
Update them together and repair navigation. Recheck source when prior evidence
depends on changed inputs. An internal refactor with no reader impact needs no
documentation rewrite; explain that judgment in the ordinary work summary if useful.

Keep unaffected material and meaningful historical evidence. Avoid whole-repository
regeneration, repeated source surveys, cosmetic churn, and duplicate status ledgers.
Use existing project records and checks; this workflow adds no scheduler, service,
recurring evaluation, or mandatory screenshot pipeline.

## Check the result

Walk through the instructions from the stated starting conditions. Check commands,
links, labels, expected results, and the consequential failure path against their
sources. Use existing validators and safe, proportionate observations where they
resolve uncertainty. Report which claims were source-reviewed or exercised and
which remain unverified. Agent review does not establish human comprehension.
Stop when the scoped reader journey is complete and its limits are explicit.
